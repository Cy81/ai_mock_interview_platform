## 原理讲解

### 1. Docker 多阶段构建

```
后端 Dockerfile 构建流程
┌─────────────────────────────────────────────────────┐
│ Stage 1: builder (python:3.11-slim)                 │
│   ├─ COPY requirements.txt                          │
│   ├─ pip install --no-cache-dir                     │
│   └─ 产出: /usr/local/lib/python3.11/site-packages │
├─────────────────────────────────────────────────────┤
│ Stage 2: runtime (python:3.11-slim)                 │
│   ├─ COPY --from=builder site-packages              │
│   ├─ COPY ./app /app                                │
│   ├─ EXPOSE 8000                                    │
│   └─ CMD ["gunicorn", "-k", "uvicorn.workers..."]   │
└─────────────────────────────────────────────────────┘

前端 Dockerfile 构建流程
┌─────────────────────────────────────────────────────┐
│ Stage 1: build (node:20-alpine)                     │
│   ├─ npm ci                                         │
│   ├─ npm run build                                  │
│   └─ 产出: /app/dist                               │
├─────────────────────────────────────────────────────┤
│ Stage 2: serve (nginx:alpine)                       │
│   ├─ COPY --from=build /app/dist /usr/share/nginx   │
│   ├─ COPY nginx.conf                                │
│   └─ EXPOSE 80                                      │
└─────────────────────────────────────────────────────┘
```

多阶段构建的核心价值：构建依赖（gcc、node_modules）不进入最终镜像，后端镜像约 150MB，前端镜像约 25MB。

### 2. docker-compose 服务编排

```
服务依赖关系图
┌────────┐     ┌────────┐
│  nginx │────>│frontend│
│  :80   │     │  :80   │
│        │────>│backend │
└────────┘     │  :8000 │
               └───┬────┘
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
     ┌────────┐┌───────┐┌───────┐
     │postgres││ redis ││celery │
     │ :5432  ││ :6379 ││worker │
     └────────┘└───────┘└───────┘
```

7 个服务：PostgreSQL(pgvector)、Redis、Backend(FastAPI)、Celery Worker、Frontend(Vue build)、Nginx(统一入口)、可选的 Flower(Celery 监控)。

关键配置要点：
- `healthcheck`：postgres 用 `pg_isready`，redis 用 `redis-cli ping`，backend 用 `/health` 端点
- `depends_on.condition: service_healthy`：确保依赖服务就绪后再启动
- `restart: unless-stopped`：进程崩溃自动重启，手动停止不重启

### 3. Nginx 反向代理配置

```nginx
# 核心配置要点（简化示意）
server {
    listen 80;

    # Gzip 压缩
    gzip on;
    gzip_types text/css application/javascript application/json;

    # 安全头
    add_header X-Frame-Options DENY;
    add_header X-Content-Type-Options nosniff;
    add_header X-XSS-Protection "1; mode=block";

    # API 代理（含 SSE 透传）
    location /api/ {
        proxy_pass http://backend:8000;
        proxy_buffering off;          # SSE 必须关闭缓冲
        proxy_cache off;
        proxy_set_header Connection '';
        proxy_http_version 1.1;
    }

    # 静态资源长缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # SPA fallback
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

SSE 透传是本项目的关键点：面试评分使用 Server-Sent Events 流式返回，必须关闭 `proxy_buffering` 否则客户端无法实时接收数据。

### 4. 测试架构设计

```
测试隔离策略
┌──────────────────────────────────────────┐
│            pytest 测试进程                │
├──────────────────────────────────────────┤
│  conftest.py                             │
│  ├─ SQLite + StaticPool (内存数据库)      │
│  ├─ respx mock (拦截外部 HTTP)           │
│  ├─ override_dependencies (替换真实服务)  │
│  └─ AsyncClient (httpx 测试客户端)       │
├──────────────────────────────────────────┤
│  无需: PostgreSQL / Redis / 真实 AI API   │
└──────────────────────────────────────────┘
```

`StaticPool` 让所有异步连接共享同一个 SQLite 内存数据库连接，避免事务隔离导致测试看不到已插入的数据。`respx` 拦截所有对 DeepSeek/DashScope 的 HTTP 请求，返回预设的 mock 响应。

### 5. Makefile 命令设计

Makefile 作为项目统一命令入口，降低团队成员的认知负担：

```makefile
test:        # 运行后端测试
build:       # 构建所有 Docker 镜像
up:          # 启动所有服务
down:        # 停止所有服务
logs:        # 查看服务日志
lint:        # 代码风格检查
migrate:     # 数据库迁移
```

## 实验步骤

### 实验一：本地运行测试套件

1. 进入 backend 目录：`cd backend`
2. 安装测试依赖：`pip install pytest pytest-asyncio httpx respx`
3. 运行全部测试：`python -m pytest -v`
4. 观察输出：确认所有测试通过，无外部服务依赖
5. 运行单个测试文件：`python -m pytest tests/test_interview_flow.py -v`

### 实验二：Docker 多阶段构建

1. 构建后端镜像：`docker build -t ai-interview-backend ./backend`
2. 检查镜像大小：`docker images ai-interview-backend`（应 < 200MB）
3. 构建前端镜像：`docker build -t ai-interview-frontend ./frontend`
4. 检查镜像大小：`docker images ai-interview-frontend`（应 < 30MB）
5. 对比：不使用多阶段构建时镜像大小（通常 > 1GB）

### 实验三：docker-compose 完整部署

1. 复制环境变量：`copy .env.example .env`，填入必要配置
2. 启动所有服务：`docker compose up --build -d`
3. 查看服务状态：`docker compose ps`，确认所有服务 healthy
4. 查看日志：`docker compose logs -f backend`
5. 访问 http://localhost，验证 Nginx 正确代理前后端
6. 停止服务：`docker compose down`

### 实验四：Nginx 配置验证

1. 访问 `/api/health`，确认代理到后端正常
2. 访问不存在的前端路由如 `/some/path`，确认 SPA fallback 生效
3. 检查响应头：确认包含安全头（X-Frame-Options 等）
4. 访问 `/assets/xxx.js`，确认 Cache-Control 包含 immutable
5. 测试 SSE 端点：确认流式数据实时到达，无缓冲延迟
