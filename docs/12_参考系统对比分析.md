# 参考系统对比分析

调研时间：2026-06-03

参考对象：

- 前台：`http://101.201.226.6:8080`
- 后台：`http://101.201.226.6:8081`

调研方式：

- 使用管理员账号登录后台观察菜单、列表、数据卡片和管理能力。
- 在前台创建临时候选人账号，仅用于观察候选人端页面结构。
- 截图和页面文本摘要保存到本地 `output/playwright/compare/`，该目录为调研产物，不纳入 Git。

## 一、总体结论

参考系统更像一个已经面向演示/运营使用的完整产品，特点是前台和后台入口分离、管理后台结构清晰、题库和知识库拆分明确、岗位模板配置更细。

我们当前系统更像一个课程型企业实战工程，优势是后端架构更完整、RAG/Agent/评分链路更系统、客户端功能更丰富，尤其是简历文本录入、岗位推荐解释、知识库引用、报告雷达图等能力已经具备。

最值得优先参考的不是视觉样式，而是后台信息架构和数据模型：

1. 把题库 RAG 和知识文档 RAG 拆成两个独立后台模块。
2. 给题库增加结构化字段：分类、岗位、难度、使用次数、向量化状态、启用状态。
3. 增加题库批量导入、全量重建、检索测试。
4. 增加候选人个人中心。
5. 优化前台首屏，让“上传简历 -> 岗位匹配 -> 开始面试 -> 看报告”的入口更直接。

## 二、参考系统功能拆解

### 1. 前台候选人端

参考系统前台菜单较少，主路径非常聚焦：

| 模块 | 观察到的能力 |
| --- | --- |
| 登录/注册 | 邮箱密码登录；注册字段包含名、姓、邮箱、密码 |
| 面试记录 | 默认首页；空状态提示上传简历开始第一次 AI 模拟面试 |
| 上传简历 | 上传 PDF 简历；填写目标岗位；上传并解析简历 |
| 岗位匹配 | 选择简历；填写期望求职方向；点击开始匹配 |
| 个人中心 | 头像占位；姓名、邮箱展示；编辑姓/名/性别/手机号/学校/求职目标/所在城市；修改密码 |

特点：

- 用户路径短，适合新用户快速理解。
- 前台没有复杂统计图，主要服务候选人完成核心动作。
- 简历上传入口和开始面试入口非常明显。
- 个人资料模块比我们当前系统完整。

### 2. 后台管理端

参考系统后台菜单：

| 菜单 | 观察到的能力 |
| --- | --- |
| 数据概览 | 注册用户、上传简历、面试总数、已完成面试 |
| 用户管理 | 用户列表；状态展示；禁用操作 |
| 面试记录 | 状态筛选：全部、进行中、已完成；列表展示岗位、难度、题数、得分、时间；详情/删除 |
| 题库管理 | 检索测试、批量导入、全量重建、新增题目；题目总数、已向量化、分类数、最高使用次数；分类/岗位/难度/状态筛选 |
| 文档管理 | 检索测试、上传文档、分类/状态筛选；展示类型、大小、分类、Chunks、索引状态；详情/禁用/重建/删除 |
| 岗位模板 | 新增岗位；分类/状态筛选；展示标签、岗位名称、分类、层级、难度、题数、排序、状态 |

后台最强的部分是“结构化运营能力”：

- 题库不是普通文档，而是独立资源。
- 知识文档和题库分开管理。
- 岗位模板包含分类、层级、难度、题数，能直接影响面试生成策略。
- 管理后台提供批量导入、全量重建、检索测试这些运维动作。

## 三、我们当前系统已有能力

### 1. 前台

当前前台路由：

| 路由 | 页面 |
| --- | --- |
| `/` | 工作台 Dashboard |
| `/resumes` | 简历解析 |
| `/jobs` | 岗位匹配 Agent |
| `/interviews` | 模拟面试 |
| `/reports` | 评分报告 |

已有优势：

- 工作台有简历、面试、报告、进行中等 KPI。
- 支持文件简历和文本简历两种入口。
- 支持 PDF / DOCX / TXT / MD，参考系统目前只看到 PDF。
- 岗位匹配 Agent 展示匹配分、匹配依据、技能差距、学习路径、知识库引用。
- 有模拟面试和评分报告模块，报告侧包含图表能力。

当前短板：

- 缺少个人中心。
- 新用户首屏较偏“系统工作台”，不像参考系统那样直接引导开始面试。
- 候选人端菜单比参考系统更多，但核心链路入口不够集中。

### 2. 后台

当前后台路由：

| 路由 | 页面 |
| --- | --- |
| `/admin` | 后台总览 |
| `/admin/users` | 用户管理 |
| `/admin/jobs` | 岗位管理 |
| `/admin/rag` | RAG 文档管理 |
| `/admin/interviews` | 面试记录 |

已有优势：

- 用户管理已经有角色字段，比参考系统列表更细。
- 面试记录已有状态筛选、分页、分数、创建/完成时间。
- 岗位管理支持必备技能、加分技能、级别、薪资范围、排序、上线/下线。
- RAG 文档管理支持上传文件、新增/编辑、重索引、启用/禁用、测试检索。
- 后端 API、模型、任务队列、RAG 服务、Agent 服务已经形成工程闭环。

当前短板：

- RAG 后台把题库和知识库放在同一个页面，通过 `rag_type` 区分；参考系统拆分后更适合运营。
- 题库缺少独立结构化字段，如分类、岗位、难度、使用次数、向量化状态。
- 缺少题库批量导入和全量重建入口。
- 文档管理缺少文件大小、Chunks、分类等运营信息展示。
- 岗位管理缺少参考系统里的“题数、难度、分类、层级”这些直接影响面试策略的字段。

## 四、核心差距表

| 维度 | 参考系统 | 我们当前系统 | 建议 |
| --- | --- | --- | --- |
| 前后台入口 | 前台 8080，后台 8081，入口分离 | 单前端应用内用 `/admin` 分区 | 可保留当前实现；部署时可增加后台独立入口 |
| 候选人首页 | 面试记录 + 开始新面试 | KPI 工作台 + 图表 | 增加“开始新面试”强入口 |
| 简历上传 | PDF + 目标岗位 | 文件 + 文本，格式更多 | 保留优势；UI 可更聚焦 |
| 个人中心 | 完整资料和改密 | 暂缺 | 建议补齐 |
| 题库管理 | 独立模块，结构化字段丰富 | RAG 文档中的一种类型 | 建议拆独立题库模块 |
| 知识文档 | 独立模块，展示大小、Chunks、分类、状态 | 与题库共用 RAG 文档页 | 建议拆独立知识文档模块 |
| 岗位模板 | 分类、层级、难度、题数、排序 | 技能、级别、薪资、排序 | 建议合并双方优势 |
| 管理动作 | 批量导入、全量重建、检索测试 | 上传、重索引、测试检索 | 补批量导入和全量重建 |
| 面试记录 | 详情/删除、难度、题数、得分 | 状态、题数、总分、创建/完成时间 | 增加详情和删除操作 |

## 五、推荐迭代优先级

### P0：运行和数据稳定性

当前本地运行已修复过两类问题：

- `DEBUG=release` 导致配置解析失败。
- 旧 SQLite 开发库缺字段导致启动失败。

这些属于开发环境稳定性，已经处理。后续应避免把本地 `.db` 和 `.db.*` 文件纳入 Git。

### P1：后台信息架构对齐参考系统

优先把 `/admin/rag` 拆成：

1. `/admin/question-bank`
2. `/admin/knowledge`

题库建议字段：

- category：technical / behavior / system_design / project
- position_code：python_backend / ai_application 等
- difficulty：easy / medium / hard
- question：题面
- answer_points：参考要点
- use_count：使用次数
- vector_status：是否向量化
- is_active：启用状态

知识文档建议字段：

- title
- file_type
- file_size
- category
- chunk_count
- index_status
- uploaded_at
- is_active

### P2：岗位模板增强

在现有岗位管理基础上补：

- category：backend / frontend / ai / mobile / devops
- level：junior / mid / senior
- difficulty：easy / medium / hard
- question_count：默认题数

这样岗位模板可以直接驱动面试题生成策略。

### P3：候选人端体验增强

建议增加：

- 个人中心：基础资料、求职目标、城市、学校、改密。
- 首页强入口：上传简历、开始新面试、查看报告。
- 空状态引导：无简历、无面试、无报告时，给明确下一步按钮。

### P4：后台运营能力

建议补：

- 题库批量导入。
- 题库全量重建向量。
- 文档重建索引进度。
- 面试详情抽屉。
- 面试删除操作。
- 管理后台更多统计卡片。

## 六、结论

参考系统适合作为“产品化后台和用户路径”的参考，我们当前系统适合作为“工程架构和 AI/RAG/Agent 链路”的基础。

最优做法不是照抄参考系统，而是把它的运营后台拆分方式、题库结构化字段、岗位模板字段、个人中心和新用户引导吸收到我们现有系统里。这样既保留我们当前的工程深度，也能补上参考系统更成熟的产品管理能力。
